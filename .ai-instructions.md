# AI Development Instructions

## Code Quality Requirements

After **EVERY** code change or file modification in this project:

1. **Run ESLint auto-fix** on modified files:

   ```
   npm run lint:fix
   ```

2. **Run Prettier formatting** on modified files:

   ```
   npm run format
   ```

3. **Verify no linting errors** (must pass):

   ```
   npm run lint
   ```

4. **Verify formatting is correct** (must pass):

   ```
   npm run format:check
   ```

5. **Unit tests** before calling work done:

   ```
   npm run test:unit
   ```

6. **Fireguard** when unit tests were added or modified:

   ```
   npm run fireguard
   ```

7. **Type checking** (recommended before commits):

   ```
   npm run type-check
   ```

8. **Deadcode** before calling work done:

   ```
   npm run deadcode
   ```

9. **Build** before calling work done:

   ```
   npm run build
   ```

10. **E2E** when UI/navigation/routes change:

    ```
    npm run test:e2e
    ```

11. **Red team review** before calling work complete / merge-ready (mandatory):

    Follow `.cursor/skills/red-team-review/SKILL.md` (mirrored as
    `antagonistic-pr-review`). Post the review on the PR, fix every **Blocking**
    finding, then re-run the gates above. **Do not report completion** with an
    unresolved red-team review.

## When to Run

- ✅ After creating new files
- ✅ After editing any `.ts` or `.tsx` files
- ✅ After editing configuration files that affect code style
- ✅ Before confirming any task is complete

## Execution Order

Always run in this order:

1. `npm run lint:fix`
2. `npm run format`
3. `npm run lint`
4. `npm run format:check`
5. `npm run test:unit`
6. `npm run fireguard` (when unit tests added/modified)
7. `npm run type-check`
8. `npm run deadcode`
9. `npm run build`
10. `npm run test:e2e` (when UI/routes change)
11. **Red team review** (`.cursor/skills/red-team-review/SKILL.md`) — post on PR; fix Blocking; re-verify

## Red team review (hard gate)

This is a **required AI gate**, not optional polish.

- Required for every implementation PR / ticket close-out that changes product
  code, tests, CI, workflows, or agent skills — **including work you authored**.
- Assume the change is trying to look done while hiding soft failure modes.
- Attack correctness, security, test honesty, gate evasion, CI reality, scope
  creep, and operability (see the skill for the full checklist).
- Post with marker `<!-- red-team-review -->` (also accept legacy
  `<!-- antagonistic-pr-review -->`).
- **Blocking** findings = failed delivery until fixed and pushed.
- Skip only for pure docs typo fixes with no behavior change, or when the user
  explicitly waives the review.
- Summarize the red-team outcome in your completion report (verdict + what you
  attacked). Claiming “done” without this is a process failure.

## CI parity: local `act` vs cloud draft PR

- **Local runs only:** After the npm gate above, when Docker + [`nektos/act`](https://github.com/nektos/act) are available, run `act` before merge-ready on substantial work — especially CI/workflow changes (e.g. `act pull_request -W .github/workflows/pr-checks.yml`). Skip jobs that need unavailable secrets/services and say so. If `act` is unavailable, say so and use a draft PR + real Actions.
- **Agentic cloud runs:** Do **not** run `act`. Open a **draft** PR and rely on real GitHub Actions. Keep it draft while checks are pending or failing. When CI Checks jobs `test`, `fireguard`, `lint`, and `build` are green (and red-team **Blocking** items are clear), mark the PR **ready for review**.

## Important Notes

- **Do not skip these steps** — they are mandatory for all code changes
- If lint, format, or tests fail, fix the issues and re-run until passing
- The goal is zero warnings and 100% code quality compliance
- Board / TDD / delivery gate: see `.cursor/skills/delivery-standards/SKILL.md`
- Stack playbooks: `docs/stacks/react-pages.md`, `docs/stacks/electron.md`
